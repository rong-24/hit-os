## 2. 当进入和退出 `system_interrupt` 时，都发生了模式切换，请总结模式切换时，特权级是如何改变的？栈切换吗？如何进行切换的？

> 1. 进入 system_interrupt  
>    - 特权级切换：用户态程序通过 `int 0x80` 调用系统中断，用户态（特权级 3）$\to$ 内核态（特权级 0）  
>    - 栈切换：CPU 自动从 TSS 中加载内核态的 SS 与 ESP，并将用户态的 SS、ESP、EFLAGS、CS、EIP 压入内核栈  
>
> 2. 退出 system_interrupt  
>    - 特权级切换：内核态程序通过 `iret` 返回用户态程序，内核态（特权级 0）$\to$ 用户态（特权级 3）  
>    - 栈切换：CPU 自动从内核栈弹出用户态的 SS、ESP、EFLAGS、CS、EIP，并加载相应寄存器

*最后，简述发生这些变化的原因。*

> 相关代码如下（时间片中断处理程序）：  
>
> ```asm
> /* Timer interrupt handler */
> .align 2
> timer_interrupt:
>     push %ds
>     pushl %eax
>     movl $0x10, %eax        # 首先让 DS 指向内核数据段。
>     mov  %ax, %ds
>     movb $0x20, %al         # 然后立刻允许其他硬件中断，即向 8259A 发送 EOI 命令
>     outb %al, $0x20
>     movl $1, %eax           # 接着判断当前任务，若是任务 1 则去执行任务 0，或反之
>     cmpl %eax, current
>     je   1f
>     movl %eax, current      # 若当前任务是 0，则把 1 存入 current，并跳转到任务 1
>     ljmp $TSS1_SEL, $0      # 去执行。注意跳转的偏移值无用，但需要写上。
>     jmp  2f
> 1:  movl $0, current         # 若当前任务是 1，则把 0 存入 current，并跳转到任务 0
>     ljmp $TSS0_SEL, $0      # 去执行
> 2:  popl %eax
>     pop  %ds
>     iret
> ```
>
> 从 Task 0 切换至 Task 1 的关键指令为 `ljmp $TSS1_SEL, $0`，在 Bochs 中对应可见为 `0x008:0x149` 处的 `jmpf 0x30:0x00`。该指令触发的是 **硬件任务切换**（Task Switch），其执行细节如下：  
>
> 1. **通过 GDT 找到目标 TSS 段描述符**：`TSS1_SEL = 0x30` 是 GDT 中的选择子。处理器根据选择子的索引（`0x30 >> 3 = 6`）访问 GDT 的第 6 个条目并取出对应描述符。  
> 2. **加载新的 TSS 并完成上下文切换**：处理器使用描述符给出的基地址定位目标 TSS（即 TSS1）的内存位置；随后将当前任务的现场保存到当前 TSS（TSS0），并从目标 TSS（TSS1）中装载新任务的寄存器上下文，包括：  
>    - `CS` / `EIP`：确定新任务的执行起点；  
>    - `SS` / `ESP`：切换并初始化新任务的栈；  
>    - 通用寄存器（如 `EAX`、`EBX` 等）与段寄存器（如 `DS`、`ES` 等）。  
>
> 因此，硬件自动完成的结果可以概括为：**任务 0 的状态被保存到 TSS0；任务 1 的上下文从 TSS1 被加载；控制流跳转到任务 1 的入口位置（`task1`）**。  
>
> 在 Bochs 的现象上，这些变化具体表现为：  
> - `GDT` 中 `0x30` 所指向的条目为目标 Task1 的 `Available 32bit TSS`；执行任务切换后，`0x30` 对应的 TSS 变为 `Busy`，而 `0x20`（TSS0）保持/恢复为 `Available`；  
> - 执行 `info tss` 时，切换前显示的是 `TSS0`，切换后显示的是当前 `TSS1`；并且 `TSS1` 中记录的寄存器值与切换后 CPU 当前寄存器值相对应，说明切换后由 TSS1 **重新加载** 了寄存器现场。

## 5. 请详细总结任务切换的过程。



### (1) 第一次切换

*需要包含以下要点：*

- 在哪条指令发生的切换？
- 如何从`TSS1` 保存的信息计算出切换后要执行的指令地址？
- 切换之后执行什么程序？

> 第一次任务切换由时钟中断 `timer_interrupt` 触发，并发生在其中的**任务切换指令（远跳转）**处：通过 `ljmp/jmpf` 跳转到任务 1 的 TSS 选择子（例如形如 `jmpf 0x30:0` 的远跳转）。  
>  
> 该远跳转会触发 CPU 的硬件任务切换机制：CPU 将当前任务的寄存器现场写入当前任务的 TSS，同时从 `TSS1` 中恢复任务 1 的上下文。由于下一条要执行的指令地址由 `CS:EIP` 决定，因此切换后要执行的位置可直接由 `TSS1` 中保存/加载得到的 `EIP`（以及对应的 `CS`）确定：**切换后入口地址即为 `TSS1.EIP`（配合 `TSS1.CS` 组成 `CS:EIP`）**。若任务 1 是首次被调度，则 `TSS1.EIP` 通常初始化为任务 1 程序的入口。  
>  
> 切换完成后开始执行**任务 1 的程序**：要么从任务 1 的入口开始运行（首次调度），要么从任务 1 上一次被切走时的断点位置继续运行（非首次调度）。

---

### (2) 第二次切换

*需要包含以下要点：*

- 在哪条指令发生的切换？
- 如何从`TSS0` 保存的信息计算出切换后要执行的指令地址？
- 切换之后执行哪条指令？
- 执行 `timer_interrupt` 最后的 `iret` ，程序可能返回的地方有哪些，包含 `system_interrupt` 内部吗，为什么？

> 第二次切换同样发生在下一次时钟中断进入 `timer_interrupt` 后的**同一处远跳转任务切换指令**，但目标变为任务 0 的 TSS（例如形如 `jmpf 0x20:0`，即跳转到任务 0 的 TSS 选择子）。  
>  
> 切换后指令地址的确定方式与第一次一致：CPU 从 `TSS0` 恢复寄存器上下文，下一条执行位置由 `CS:EIP` 决定，因此可由 `TSS0.EIP`（配合 `TSS0.CS`）得到切换后的执行地址。`TSS0.EIP` 保存的是任务 0 **上次被切换出去时**的执行点（即当时被时钟中断“打断”的位置，或者由硬件机制记录的恢复点）。  
>  
> 因而切换回任务 0 后，将继续执行任务 0 上次被打断时的那条指令序列（也可以理解为：恢复到任务 0 的断点处继续跑）。随后，当 `timer_interrupt` 走到末尾执行 `iret` 时，CPU 会从当前任务（此时是任务 0）的内核栈中弹出 `EIP/CS/EFLAGS`（若发生过特权级切换还会弹出 `SS/ESP`），从而返回到任务 0 的被中断现场对应的执行流。  
>  
> 关于 `timer_interrupt` 末尾 `iret` 的返回位置：它可能回到**当次时钟中断发生时正在运行的任务**的现场，典型情形包括：  
> - 返回到任务 0 的用户态代码（若中断发生时任务 0 正在用户态运行）；  
> - 返回到任务 1 的用户态代码（若中断发生时任务 1 正在用户态运行）；  
> - 在某些实现细节下，也可能回到对应任务的内核态路径（例如中断发生时处于内核态执行），但返回点始终由“被中断现场压栈内容”决定。  
>  
> 一般不将其理解为“返回到 `system_interrupt` 内部”，原因在于：`system_interrupt` 是由系统调用 `int 0x80` 进入的**另一条中断/陷入控制流**，其返回点由该系统调用触发时压栈保存的 `CS:EIP` 决定；而时钟中断的 `iret` 仅能回到**本次时钟中断所打断的那条执行流**。两者属于不同中断向量、不同入口，`timer_interrupt` 的 `iret` 不会“凭空跳入”系统调用处理例程内部；只有当时钟中断恰好在系统调用路径执行期间发生，`iret` 才可能回到该时刻被打断的内核执行点，但这属于“回到当时被打断的位置”，而非由时钟中断主动选择返回到 `system_interrupt` 的某个逻辑阶段。

---

### (3) 第三次切换

*需要包含以下要点：*

- 在哪条指令发生的切换？
- 如何从`TSS1` 保存的信息计算出切换后要执行的指令地址？
- 切换之后执行哪条指令？

> 第三次切换发生在再下一次时钟中断进入 `timer_interrupt` 后，仍然是在**远跳转触发硬件任务切换**的那条指令处，这一次目标再次指向任务 1 的 TSS（例如再次执行到 `jmpf 0x30:0` 这一类跳转）。  
>  
> 由于任务 1 在前一次运行过程中已经被切换出去过，CPU 在切换离开任务 1 时会把当时的寄存器现场更新到 `TSS1` 中，因此此时 `TSS1.EIP` 不再仅是“入口地址”，而是**任务 1 上次被切走时的断点地址**。切换后要执行的指令地址因此由 `TSS1.EIP`（配合 `TSS1.CS`）直接确定。  
>  
> 切换完成后继续执行任务 1：也就是从任务 1 上一次被时钟中断打断的位置（`TSS1` 中保存的 `CS:EIP`）接着向下执行。

---

### (4) 总结任务切换的整个过程

> 任务切换以时钟中断 `timer_interrupt` 为驱动，通过“中断压栈 + 保存/恢复上下文 + 远跳转触发硬件任务切换”完成在任务 0 与任务 1 之间的轮转。可按以下链路理解：  
>  
> 1) **时钟中断到来**：CPU 按 IDT 找到 `timer_interrupt` 入口并进入中断处理流程；进入时 CPU 会自动在当前栈上保存必要的返回现场（典型为 `EIP/CS/EFLAGS`，若涉及特权级变化还包括 `SS/ESP`）。  
>  
> 2) **中断处理中的额外保护现场**：在 `timer_interrupt` 内部通常还会手动保存通用寄存器与段寄存器（如 `EAX~EBP`、`DS/ES/FS/GS`），使当前任务上下文完整可恢复。  
>  
> 3) **确定下一任务**：调度逻辑选择下一任务（Linux 0.00 常见为两个任务间的简单轮转），并在 `GDT` 中定位目标任务对应的 TSS 段描述符，得到目标 TSS 选择子。  
>  
> 4) **执行任务切换指令**：在 `timer_interrupt` 中执行一次面向目标 TSS 的远跳转（`ljmp/jmpf` 到 TSS 选择子）。该指令触发 CPU 的硬件任务切换：  
>    - CPU 将当前任务的寄存器上下文写入当前任务的 TSS；  
>    - CPU 从目标任务 TSS 中装入寄存器上下文（包括 `EIP`、段寄存器、栈相关寄存器等），并更新 `TR` 指向新任务的 TSS。  
>  
> 5) **开始执行新任务**：上下文加载完成后，新任务的 `CS:EIP` 已就位；如果是首次调度则从入口执行，否则从上次被切走时的断点继续执行。  
>  
> 6) **中断返回衔接**：随后在中断处理尾部执行 `iret`，CPU 根据当前任务的内核栈弹出返回信息，使控制流回到该任务被时钟中断打断的位置，形成“时钟中断驱动、任务交替推进”的执行效果。  






## （可选）总结与反思

> 本实验围绕 Linux 0.00 的时钟中断驱动任务切换展开，通过对 `timer_interrupt` 的执行路径与 TSS 机制的梳理，可以将“任务切换”理解为一个由硬件与软件分工协作完成的闭环：中断负责提供稳定的切换时机与返回现场，调度逻辑负责决定目标任务，而硬件任务切换机制则负责在 TSS 间保存与恢复寄存器上下文，使得不同任务能够在各自的断点处继续执行。整体来看，`CS:EIP` 的恢复是任务继续运行的关键锚点；只要能明确切换时刻对应的远跳转指令、目标 TSS 的选择子以及 TSS 中 `EIP` 字段的含义，任务切换的“从哪里来、到哪里去”就能够被清晰解释。
>
> 在调试与验证过程中，一个重要收获是区分“中断入口/返回现场”与“任务上下文保存/恢复”的边界：CPU 在进入中断时自动压栈的 `EIP/CS/EFLAGS`（以及可能的 `SS/ESP`）决定了 `iret` 的返回落点，而通用寄存器与段寄存器等额外现场通常由中断处理程序显式保存，以保证执行中断处理逻辑时不破坏任务状态。与之相对，任务切换发生时对 TSS 的写入与读取，承担的是“跨任务迁移执行现场”的职责。理解这两类保存机制的不同触发条件与作用范围，有助于解释为何时钟中断的 `iret` 只能回到被该时钟中断打断的执行流，而不会任意跳转到其他中断处理程序的逻辑内部。
>
> 从系统角度看，本实验展示了早期内核在简化设计下仍能实现可用多任务的基本方法：以固定频率的时钟中断作为调度触发点，以轮转策略在少量任务间交替运行，并依赖硬件任务切换保证上下文恢复的正确性。这种实现虽然直观，但也意味着切换粒度与调度策略相对粗糙，且对中断频率、临界区保护与现场保存的完整性更为敏感。后续若进一步扩展到更多任务或更复杂的调度策略，如何在减少切换开销的同时保证现场一致性，将成为需要重点权衡的问题。
