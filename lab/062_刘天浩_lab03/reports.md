> 2. `bootsect.s` 读入 `setup.s`
>
> **bootsect.s**
>
> 为实现两阶段引导，本次将 `setup` 阶段作为后续扇区内容加载。首先在 `bootsect.s` 中明确 `SETUPLEN=2`，表示从软盘后续位置读取 2 个扇区作为 `setup.s` 的执行体，并给出 BOOT/INIT/SETUP 三段地址常量，保证加载位置与跳转目标一致。
>
> ![2-1](.\images\2-1.png)
>
> 在此基础上补充“加载 setup”的读盘逻辑：通过 `int 0x13` 的读扇区服务将 setup 装载到 `INITSEG:0x0200`，若读盘失败则先执行重置（`int 0x13, AH=0x00`）再重试，从而提升在软盘读盘场景下的鲁棒性；读盘成功后再跳转到 `SETUPSEG:0` 开始执行 setup 阶段代码。
>
> ![2-2](.\images\2-2.png)
>
> **setup.s**
>
> `setup.s` 作为第二阶段入口，首先完成段寄存器初始化，随后输出 “Now we are in SETUP” 作为阶段性标识；在此之后继续扩展硬件参数获取与打印逻辑（见第 3 部分）。
>
> ![2-3](.\images\2-3.png)
>
> ![2-4](.\images\2-4.png)
>
> **Makefile**
>
> 为使构建流程能够生成仅包含 `bootsect + setup` 的引导镜像，本次在 `linux-0.11/Makefile` 中补充 `BootImage` 目标，调用 `tools/build.sh` 进行镜像打包，并将第三参数显式设置为 `none`，用于标识“本次不需要 system 模块”。
>
> ![2-5](.\images\2-5.png)
>
> **build.sh**
>
> 由于默认构建脚本主要面向 `bootsect + setup + system` 的组合，本次在 `tools/build.sh` 中保留原有 system 写入路径的同时，补充/兼容 `system=none` 的情况：当第三参数为 `none` 时跳过 system 写入相关步骤，从而使 `BootImage` 目标能够在无 system 的条件下正常生成可启动镜像。
>
> ![2-6](.\images\2-6.png)
>
> 实验结果如下，启动阶段能够连续输出 boot 阶段自定义信息与 setup 阶段提示信息，证明第二阶段加载与跳转生效。

> 3. `setup.s` 获取基本硬件参数
>
> 在进入 setup 阶段后，本次进一步获取并展示关键硬件信息，形成更完整的“自举—加载—探测—输出”的实验闭环。
>
> 获取内存参数：通过 BIOS 扩展内存查询接口 `int 0x15, AH=0x88` 获取扩展内存大小（KB），写入变量 `memory`，随后按“Memory: + 十六进制数值 + KB”的格式输出；并在此之后调用硬盘参数表复制过程，为后续磁盘几何参数输出做准备。
>
> ![3-1](.\images\3-1.png)
>
> 获取第一硬盘参数：通过访问中断向量表获得 `INT 41h` 指针（硬盘参数表地址），将该表的 16 字节内容复制到 `INITSEG:0x0080`（即物理地址 `0x90080`）保存；复制完成后恢复 `DS=SETUPSEG`，确保后续字符串输出与数据访问不受影响。
>
> ![3-2](.\images\3-2.png)
>
> 打印数据：为降低寄存器来回切换的复杂度，本次统一设置 `ES=INITSEG`，直接使用段覆盖读取 `ES:0x80 / ES:0x82 / ES:0x8E` 处的数据，分别输出 Cylinders、Heads、Sectors 等字段，并对 Heads/Sectors 做低字节截取以得到可读值。
>
> ![3-3](.\images\3-3.png)
>
> 同时，为了适配 16 位环境下的稳定输出，本次采用 `int 0x10, AH=0x0E` 的逐字符方式实现字符串打印过程 `print_str`（输入为 `DS:SI` 与 `CX`），为各类信息输出提供统一基础能力。
>
> ![3-4](.\images\3-4.png)
>
> 实验结果如下：在 bochs 完整启动窗口中可见 boot 阶段自定义信息、setup 阶段提示信息以及 Memory 等硬件参数输出，表明参数获取与打印流程工作正常。
>

## 回答如下问题：

### 有时，继承传统意味着别手蹩脚。 `x86` 计算机为了向下兼容，导致启动过程比较复杂。 请找出 `x86` 计算机启动过程中，被硬件强制，软件必须遵守的两个“多此一举”的步骤（多找几个也无妨），说说它们为什么多此一举，并设计更简洁的替代方案。

> 1. 复位后强制从 16 位实模式启动，再切换到现代执行环境  
> 为什么多此一举：x86 为兼容 8086/8088，CPU 上电复位默认进入实模式，地址空间与保护机制受限；现代操作系统需要更统一的执行模型（更高位宽、隔离机制、分页等），因此引导阶段必须额外完成模式切换相关的准备与跳转流程，增加了代码复杂度与故障面。  
> 更简洁的替代方案：由硬件或固件约定“上电即提供受保护的统一执行环境”（例如直接提供 32/64 位模式与平坦地址视图），固件完成必要初始化并以结构化参数传递启动信息，操作系统直接进入内核入口而无需在早期阶段手动切换模式。
>
> 2. MBR/引导扇区 512 字节限制与固定签名（0xAA55），迫使多阶段引导  
> 为什么多此一举：引导扇区硬性限制为 512 字节且必须携带固定签名才能被识别为可引导，导致引导程序无法一次容纳完整功能，只能分阶段加载（stage1/stage2…）；多阶段链条需要额外读盘、跳转与布局约束，调试成本更高，也更容易引入兼容性问题。  
> 更简洁的替代方案：固件提供文件级加载能力，允许从可识别的分区/文件系统直接加载较大引导程序或内核映像，不受 512 字节限制，并通过标准化结构传递启动参数，从而减少“拼扇区+多级跳转”的历史负担。
>
> 3. A20 Gate 等历史兼容开关  
> 为什么多此一举：为了兼容早期地址回绕语义，一些平台需要显式开启 A20 才能稳定访问 1MB 以上内存，该步骤对现代系统无实际收益，但会在早期引导阶段引入额外探测与分支处理。  
> 更简洁的替代方案：硬件/固件保证上电默认开启 A20（或彻底取消回绕语义），操作系统无需额外开关与兼容处理。
>
> 4. 早期对 BIOS 中断服务的强依赖  
> 为什么多此一举：实模式下使用 BIOS 中断（如 int 0x10/0x13/0x15）完成显示、读盘与取参，会让引导路径强依赖固件接口；进入现代模式后操作系统还需重新建立自身驱动与设备抽象，相当于前期做了一套“临时接口”随后推倒重来。  
> 更简洁的替代方案：固件仅提供一次性“枚举+加载+参数表”服务，操作系统尽快接管硬件并由自身驱动完成显示与 IO，减少早期阶段对 BIOS 中断生态的依赖。

## （可选）总结与反思

本次实验从引导扇区的最小输出与读盘出发，完成了 boot 阶段重定位、加载 setup、跳转执行，并在 setup 阶段通过 BIOS 中断与中断向量表获取硬件参数并打印。实现过程中需要严格控制早期环境的边界条件，包括 512 字节约束、段寄存器与内存布局、读盘参数与失败恢复、以及字符输出在 16 位模式下的稳定性。实验也直观体现了 x86 向下兼容带来的复杂度成本：实模式起步、多阶段加载、历史开关与固件接口依赖等。理解这些历史包袱后，更能认识到启动流程分层设计的意义：在极度受限的最初阶段建立可靠的“信任链”，为后续系统加载与运行奠定基础。
